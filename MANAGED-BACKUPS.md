# Managed encrypted backups · FirmQuill Full Suite

Managed backups are optional, local to the Full Suite server, and **off by default**. They use the existing password-protected whole-database `.fqdb` format. The current 64 MiB logical database limit is unchanged. This feature does not send backups anywhere, certify a restore, or replace independent protected retention and recovery rehearsals.

## Host provisioning

1. Use one active Full Suite host process for this database. Create a dedicated backup directory on a local filesystem that supports atomic rename and hard links. Keep it outside the application directory, and keep the database and recovery key outside the backup directory. Use an encrypted volume and a service-private directory to protect retention state and staged files. Restrict directory/key to the service account and designated recovery operator (on POSIX use directory mode 0700 and a key file mode 0600; on Windows apply equivalent private NTFS ACLs). Use distinct storage and secrets for staging versus production.
2. Create a separate protected file with an independently generated high-entropy recovery password: 32–256 printable ASCII characters without spaces, optionally followed by one newline. For example, generate 32 bytes with a trusted cryptographic random source and encode them as base64. Do not reuse a login password or check a key into source control. Keep a protected recovery copy separate from the archives and service host. Existing archives need the very password with which they were created; do not destroy an old key when changing the current one. Identity connector keys and optional FTPS credentials are separate from this password and are not included in a database archive.
3. Set **FIRMQUILL_BACKUP_DIRECTORY** and **FIRMQUILL_BACKUP_KEY_FILE** to the two absolute paths in the server's private launch configuration, then restart. These are *paths only*, not the actual password. If either is missing, invalid, or unreadable, the host still starts and unrelated workflows remain available. The product does not place production credentials on GitHub or expose paths in the ERP UI.

## Owner policy and receipts

1. Main ERP owner opens **Managed backups → Edit backup policy**. A daily time is one **UTC** time, blank to disable. The host checks approximately once per minute, runs only when up at or after the scheduled time, never replays earlier dates, and deduplicates today across restarts. A scheduled storage failure is retried no more frequently than every 15 minutes.
2. **Require an encrypted backup immediately before an approved AI proposal or reviewed Lite import writes records** protects two existing posting actions: approving an optional agent's contact/item addition, and confirming an encrypted Lite import into an empty workspace. The trigger is not a booking, upload to support, staging/preview, rejection, generic bank import, or building a package for a separate first-run installation. The archive is captured before posting; while encryption is running, unrelated workflows are not locked. If any intervening DB write changes the recovery point, the pending approval or preview remains outstanding. Recheck the current data and retry. Stale attempts can leave a usable archive of an earlier state, but they cannot authorize a write.
3. Keep **2–10** managed archives. After successfully publishing a new encrypted archive and recording its status, the host removes only older app-managed archives for this installation. It doesn't touch manual archives or another installation's prefix and doesn't delete the previous archive to make room for a failed backup. Where needed, preserve higher-retention/off-host copies separately. A copy stored on the same host alone cannot protect against total host loss. Inspect private staging files after an unclean shutdown; an orphaned daily filename will prevent duplicate scheduled writes for that day but is explicitly not treated as recorded complete.
4. Refresh to see the **Last completed encrypted archive still present**, when recorded. This shows a real archived snapshot, timestamp, trigger and logical data size. It does not claim newer backups are good, report external backups, or establish that an archive has been test-restored. An archive can be encrypted and published yet still need a restore rehearsal. A capacity failure, existing conflicting daily artifact, or storage failure appears as an owner status. If backup policy is opted in, the protected write will not proceed unbacked; only that action needs retry.

## Restore rehearsal and rollback

Use the existing recovery utility in an interactive terminal from the installed application directory: `node recovery.mjs restore existing.fqdb fresh-test.sqlite`. Enter the corresponding recovery password when prompted. The restore destination must be new. Start the same approved app on that copy with backups, outbound connectors and customer integrations disabled, and verify company totals, roles, recent records, worker portal and the affected operation. A restored copy retains the backup policy stored in the DB; leaving its managed host variables unset prevents scheduled writes in rehearsal. Do not link the isolated test host to production backup paths.

Rolling back a live installation is a separate authorized maintenance action. Stop/suspend writes, preserve a verified current-state archive/local snapshot, and rehearse a restore into a *different* database first. Identify which later legitimate activity would be lost or must be replayed. Restoring a whole pre-import archive replaces the **entire database as of the snapshot**, including unrelated entries, messages, worker records and approvals saved afterward. It is not an undo button, selective transaction rollback, automatic failover, or authorization to overwrite production.
